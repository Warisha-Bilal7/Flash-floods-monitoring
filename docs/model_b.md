# Model B — snowmelt / rain-on-snow LSTM

## Summary
Model B estimates a 6-hour flood-risk probability for each monitored KP basin and
hour, emphasising snowmelt, rain-on-snow and temperature/freezing-level drivers.
It publishes the §3.7 nine-column parquet contract and never shares training code
or weights with Model A.

## Architecture (frozen)
- **Deep model:** 1-layer LSTM, 48 hidden units, dropout 0.2 before a sigmoid head.
- **Constraints:** `MAX_LSTM_LAYERS=1`, hidden units in `[32, 64]` (enforced in
  `floodwatch.models.model_b.TrainConfig` and pinned by tests).
- **Lookback / horizon:** 72 h lookback, 1 h stride, 6 h label horizon.
- **Training:** Adam, BCE loss, early stopping on validation PR-AUC, fixed seed,
  CPU-only (`torch.set_num_threads(1)`).
- **Determinism:** fixed seeds and train-only standardisation statistics are saved
  in the checkpoint.

## Baseline (mandatory)
A deterministic degree-day heuristic uses accumulated melt, rain-on-snow and snow
depth, normalised from train rows only. If the LSTM does not beat the baseline on
validation PR-AUC, the published `source` becomes `baseline` and the manifest
records `baseline_wins: true`.

## Features
The model consumes the Model B temporal sequence from `floodwatch.features`:
`rain_1h`, `rain_3h`, `rain_24h`, `rain_72h`, `rain_fcst_mm_3h`, `temp_c`,
`temp_fcst_c`, `freezing_level_m`, `soil_moisture`, `snow_depth_mm`,
`snowmelt_mm`, `degree_day_melt`, `rain_on_snow`, `terrain_susceptibility`.

`top_drivers` are heuristic, human-readable summaries derived from current melt /
rain-on-snow / snow-pack values; they are not SHAP or causal attributions.

## Published artefacts
- `artifacts/b/model_b.pt` — checkpoint (gitignored binary).
- `artifacts/b/predictions_b.parquet` — §3.7 contract, train+validation rows only
  (gitignored binary; interface validated via golden fixtures).
- `artifacts/b/metrics_b.json` — validation metrics for deep vs baseline.
- `artifacts/b/manifest.json` — module, seed, snapshot hash, sha256, provenance.

## Current prototype status
The committed prototype metrics come from the synthetic demo dataset generated by
`scripts/00_build_demo.py`. The manifest records the data snapshot hash and seed;
`docs/TEST_REPORT.md` is created only by the one-shot M7 guard
(`scripts/07_test_eval_once.py`) and must not be produced during development.

## Known limits
- Synthetic demo labels are not a substitute for observed flood impact labels.
- Driver weights are descriptive summaries, not calibrated explanations.
- Temperature and snow inputs are hourly point/grid summaries; local micro-climates
  and infrastructure failures are out of scope.
- The model supports decision triage in shadow mode; it must not auto-page without
  the verification and delivery locks.
